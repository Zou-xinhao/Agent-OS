# 协作规范（三人小队）

## 1. 分支模型

```
main        只用于最终提交快照（比赛截止时从 dev 打一次）
dev         集成分支，永久存在，任何时刻必须可 make qemu 进 shell
feat/a-proc A 的日常分支
feat/b-sys  B 的日常分支
feat/c-test C 的日常分支
tag w1..w6  每周日合并后打一个，作为过程性资料
```

**所有进入 dev 的代码都走 Merge Request（MR）**，dev 设保护分支：不允许直接 push，至少 1 人 review。

## 2. 每日节奏

| 时间 | 动作 |
|---|---|
| 每天开工前 | `git switch dev && git pull --rebase` → `git switch feat/xxx && git rebase dev` |
| 每天 22:00 | 15 分钟语音站会：昨天做完什么 / 今天做什么 / 卡在哪（卡超 1 小时必须说） |
| 每天睡前 | 必须 push 一次，哪怕代码没写完（`git commit -m "wip: ..."` 也行） |
| 周三晚 | 只对齐接口，不讨论功能 |
| 周日 | 合并到 dev → 打 tag → 录 30 秒 demo 放 `demo/wN.mp4` |

## 3. 提交规范

```
[任务号][范围] 一句话说明

例：
[A1] 任务一: PCB 增加 agent_type/heartbeat_interval 字段
[B2] 任务二: 实现 sys_tool_call 的请求解码与错误码
[C0] 测试: 增加 context_push 越界用例
[D0] 文档: 补充架构图与上下文区内存布局
```

- 一条 commit 对应一个可编译状态。
- 共享文件（`kernel/syscall.h` `kernel/syscall.c` `kernel/defs.h` `Makefile` `user/user.h`）改动**必须单独一条 commit**。
- 禁止 `force push` 到 dev；禁止一次提交上千行。

## 4. MR 规范

- 标题：`[A] 任务一 完成` 这种，正文写「做了什么 / 怎么验证的 / 影响谁」。
- 行数 ≤ 400 行，超了先拆。
- 作者自己先跑通 `make qemu` 再提。
- reviewer 30 分钟内响应；只提阻塞性问题，风格问题不提。

## 5. 冲突预防三条硬规则

1. **syscall 桩由 A 一次性铺完**：16 个 case 全部存在（都返回 `E_NOSYS`），之后各人只改自己编号那几行。
   这样 `syscall.c` 从"结构性冲突"降为"几乎不冲突"。
2. **共享文件改动先报备**：群里发「我要改 syscall.h 加编号 26」，另外两人确认后再动。
3. **Makefile 只有 A 动**：B/C 需要新目标就提 issue。

冲突真发生：`git rebase dev` → 手改 → `git add` → `git rebase --continue`。
**不要用 `git merge dev`**，历史变网状后评审看 diff 会很痛苦。

## 6. 谁负责什么文件

| 文件 | 主责 | 其他人 |
|---|---|---|
| `kernel/proc.c` `proc.h` `vm.c` `trap.c` `sysproc.c` `agent_ctx.c` | A | 只读 |
| `kernel/syscall.c` `sysfile.c` `fs.c` `file.c` `log.c` `agent_tool.c` `agent_proto.h` | B | 只读 |
| `user/` `scripts/` `docs/` `README.md` `demo/` | C | 只读 |
| `kernel/syscall.h` `kernel/defs.h` `Makefile` | A（统一维护） | 提需求 |

## 7. 求助信号

出现以下情况，立刻在群里说，不要自己扛：

- 卡 1 小时没有任何进展（不是"快好了"，是"没进展"）。
- 需要改别人负责的文件。
- 某个验收标准看起来做不到了（当天说，砍范围比延期好）。
- 内核出现随机 panic（能稳定复现的可以自己查，随机的必须一起看）。

## 8. 大文件

视频/截图放 `demo/`，单个文件 ≤ 50 MB；平台仓库不一定支持 Git LFS，先压缩再传。
每周的 30 秒 demo 是解说视频的素材，别等到最后一周才录。
